# n8n workflow tooling

Twelve n8n automations that are **generated by Python scripts rather than clicked together
by hand**, plus the two shared checks every one of those scripts runs before it hands over
a file.

Each folder holds a build script, its sample data, and the workflow JSON that script writes.
The JSON imports straight into n8n. It runs on pinned sample data, so you can open one and
step through it without credentials or a live account of your own.

```
python build/build.py
```

Run that inside any demo folder and it rebuilds the workflow from scratch, checks it, and
prints what it found.

## Why generate the file instead of building it in the editor

Dragging nodes is faster the first time. It is slower every time after that. There is no
diff, no way to see what changed between two versions, no way to apply one fix across twelve
workflows, and no way to tell whether the thing you imported is the thing you tested. A
mistyped node name breaks a connection without any warning at all, and the place that turns
up is usually on a call.

Writing the JSON from a script moves all of it into text, where the checks below can run on
every build.

I should say what this costs, because it is not free. A Code node would be shorter than the
built-in nodes in maybe half of these workflows, and I still do not use one. Whoever inherits
the workflow has to be able to read the canvas without opening anything, and a screen of
JavaScript takes that away from them.

## The two checks

**Every connection points at a node that exists.** Each script walks the connection map and
fails the build if a wire references a node name that is not on the canvas, or if a node
sits there with nothing reaching it. n8n does not complain about either one on import. The
workflow simply does less than expected.

**Node version numbers get corroborated across the library.** Every node in an n8n file
carries a version, and those are written by hand into the JSON. `node_versions.py` compares
all twelve workflows: a version used by two or more of them was arrived at independently
twice and counts as evidence, a version used by exactly one has been confirmed by nobody.

```
$ python node_versions.py
35 node versions across 12 demos

CONFIRMED BY TWO OR MORE DEMOS: 19
USED IN ONLY ONE DEMO - nobody has confirmed these: 16

agency-monthly-report - open these first on import:
    n8n-nodes-base.filter@2.2
    n8n-nodes-base.splitInBatches@3
inquiry-to-crm - every version confirmed elsewhere
```

That is not proof anything is wrong. It is the difference between handing someone a file and
hoping, and handing them a file with a note saying which three nodes to open first.

Each build script calls the same function for its own workflow and prints its unconfirmed
versions at the end of every run.

## The third tool

`sticky_text.py` undoes hard line wrapping in sticky-note text. Notes are written inside the
build scripts as normal Python strings wrapped at about 78 columns so the source stays
readable, and n8n keeps every one of those newlines as a real line break. A paragraph written
as three tidy source lines arrives on the canvas broken in three places that have nothing to
do with the width of the note. This joins the paragraphs back together at build time so the
scripts can keep their readable wrapping.

## Checks that run inside the individual builds

Beyond the two shared ones, each script asserts something about its own subject. A few
examples:

- `inquiry-to-crm` states in its sample data which of six enquiries should match a customer
  record confidently, which should come back as a maybe, and which should not match at all.
  The build fails if the matching rules produce a different answer.
- `agency-monthly-report` checks that the pinned data still exercises both endings, the one
  where a report is written and the one where it is held back.
- `realestate-to-instagram` prints the price shown for each property so a formatting change
  is visible in the build output rather than on a published post.

## How the AI is kept in check

Every one of these was built for a brief where somebody would eventually ask how they know
the model will not invent something. There are four answers, and most of the workflows use
two or three together.

1. Only show it what it is allowed to see. `str-guest-messages` joins each guest message to
   that one property's guide, so the other properties are never fetched and there is nothing
   available to leak. `ask-our-documents` does the same thing through tool scope, where the
   agent can only reach three read-only sheets. This is the strongest of the four. It is also
   the only one that cannot be seen anywhere on the canvas, which is the reason it is written
   down here.
2. Do not let it run. A branch that reaches a person or a log instead of the model. Someone on
   the do-not-contact list never reaches the writer, and a figure that did not reconcile never
   reaches the briefing.
3. Check what it produced. Used where something has to be written and then judged. Weakest of
   the four, because by the time it runs the bad output already exists.
4. Do not use a model. `inquiry-to-crm` has none, on purpose. It made for a less impressive
   demo and a more reliable piece of software, and on identity matching I would make that
   trade every time.

## Layout

```
node_versions.py          compares node versions across every workflow
sticky_text.py            unwraps sticky-note text before it goes into the JSON
BUILD-RULES.md            the constraints every build follows
<demo>/build/build.py     writes the workflow, then checks it
<demo>/sample-*.json      the data pinned into the workflow
<demo>/*.json             the generated workflow, ready to import
```

Python 3.12, no dependencies outside the standard library.
